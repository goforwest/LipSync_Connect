# 4.5.x follow-up backlog — what shipped, what's bench-pending

Companion to `bench-session-2026-10-16.md` (the 4.5.0 validation cycle that
spawned these items). Firmware version for the follow-up release: **4.5.1**
(`firmware-release-pipeline` @ `3e7cc88`, pushed to the `fork` remote; app
`main` @ the hub-remote re-sync commit). Everything below is built, gated
(lint/typecheck/format/333+ unit tests/e2e/cross-check/LSTimer host suite)
and pushed; nothing is claimed verified on hardware without the bench steps
listed.

## Item 1 — Gamepad-mode BH telemetry — SHIPPED (bench-pending)

Firmware `a97e9d6`. `LSUSBGamepad` now carries the mouse's counter family
(reportAttempts before the readiness gate, reportSuccesses after TinyUSB
accepts, nonzeroReports/maxAbsReport from the 128-centered axis deltas, a
timedOut latch set only when refused while the host had configured the
composite), and `fillUsbHidDiagnostics` branches on `g_operatingMode` so
`BH,0:0` reports the ACTIVE mode's interface at the same nine indices —
no wire change, no app parser change (the health check reads only the
first six values).

**Bench:** on a 4.5.1 gamepad boot, BH should read `hidReady=1` with
attempts/successes climbing together while the stick moves and `maxAbsReport`
tracking real deltas.

## Item 2 — Settings-file size budget — SHIPPED (bench-pending)

Firmware `b5899c2` + app `0be7b5c`. `CONF_SETTINGS_FILE_BUDGET = 480`
(margin under firmware 4.1.0's 512-byte reader — the downgrade cliff);
LSMemory refuses over-budget writes (bool returns, one ERROR line naming
key/size/reason), every serial setter answers the existing FAIL,3 on a
refused store, the calibration corner store reports honestly, `EX,0:0`
opens with `SUCCESS,0:EX,0:SIZE:<bytes>/<budget>` from the new
`LSMemory::size()` (filesystem truth, not the 512-buffer view), and
`tests/settings-size.test.mjs` is the desk tripwire (default 299 B,
fully-populated worst case 409 B, budget 480 B — self-skips without a
firmware checkout, cross-check convention).

**Bench:** confirm the EX SIZE line against a real device's file (the
~383 B figure from the bench included a real device ID); optionally attempt
an over-budget write via a packed switch-remap set to see FAIL,3 (cannot be
reached with today's key set — the guard is headroom).

## Item 3 — LSTimer pool hygiene — SHIPPED (bench-pending, mystery narrowed)

Firmware `d2d1003` + app `b6056c3`. Five concrete defects fixed (see the
commit for the full evidence trail): ignored -1 registrations (now counted
+ rate-limited print + a setup()-time audit of all nine boot ids),
mid-response deleteTimer prints (now silent + counted), the missing
negative-id bounds (deleteTimer(-1)/restartTimer(-1) were out-of-bounds
writes into adjacent .bss globals — the plausible corruption mechanism
behind cross-object damage), the immediate-first-fire of 0-delay intervals
(startDelay>0 now enables the offset; disabled timers keep their anchors
advancing so enable resumes within one interval, no burst), the
single-static method-timer collision (per-method trampolines; LSScreen's
seven degraded-boot call sites ported), plus the stopwatch slot-steal and
MAX_TIMERS 10 → 16. The host harness (`dev/firmware/lstimer-test/`, wired
into `npm test` via `tests/lstimer.test.mjs`, ASan+UBSan) locks down all of
it — 92 checks.

**The safe-mode interval death (the heartbeat capture's mystery): the
reproduction attempt RAN and PASSED** — the exact boot pool with
toggleSafeMode's disables, ten minutes of virtual time at loop granularity:
the watchdog interval fires 120/120, input and screen never miss, no
corruption under sanitizers. Conclusion: the pool's own logic cannot
produce the observed death; the out-of-bounds -1 write vectors that COULD
(notably `restartTimer(-1)` from the input/pressure state machines, writing
into whatever global precedes a pool) are now closed at the source. The
loop()-feed of the watchdog (`ac90b08`) deliberately STAYS as belt-and-braces.

**Bench (next degraded/safe-mode capture):** HB lines should show the feed
tracking the loop with no mid-response LSTimer ERROR prints; a pool
exhaustion (if ever) now names itself once per 30 s instead of corrupting
transcripts; first joystick/pressure ticks now land one full interval after
boot (by design — confirm nothing in the boot feel regressed).

## Item 4 — LK remote-control drift — SHIPPED (bench-pending)

Firmware `3e7cc88` + app `c3e037d`. New read endpoint `CH,0:0` →
`SUCCESS,0:CH,0:active,page,row` (version-gated at 4.5.1 in the app; never
sent to older firmware); `modeLockedPage()` now names itself
(MODE_LOCKED_PAGE 32) so a refusal is distinguishable from "still on the
Mode options". The app's remote advances optimistically as before, then
re-syncs from device truth after every press: a locked select lands the
mirror on the locked-page notice (not a phantom mode-confirm), dropped
frozen-window presses no longer advance the cursor past the device, and
device-driven page transitions get a follow-up poll at the device's own
dwell (the locked page's return to Mode row 0 included). MANUAL pushes now
refresh a visible value screen. Tests model the drift sources directly
(locked-refusal acks, frozen-window drops, lazy transitions); the
older-firmware test pins the gate.

**Bench:** with LK set on a 4.5.1 device, refuse a mode select from the
remote — the mirror must show the locked page and then land on
MOUSE USB at row 0 when the Hub does; also walk the physical Hub menu with
the remote open (MANUAL reseed).

## Item 5 — XENSIV TLx493D migration — BRANCHED, AWAITING BENCH (do not merge)

Branch `xensiv-tlx493d-migration` @ `5285957` (pushed to `fork`; the release
branch is untouched). Vendored Infineon's `arduino-xensiv-3d-magnetic-sensor-tlx493d`
v1.1.2 (provenance + boundedness audit in `LIPSYNC.md`), ported LSJoystick
(one bounded I2C read per poll through the vendored Wire — XENSIV's A1B6
default is master-controlled continuous measurement, so no wake/write/wait
cycle at all; getZ preserved from the same snapshot; scale parity verified
in source at 0.098 mT/LSB; bus-crawl backoff untouched). The old TLV493D
fork stays in place (out of the build graph) until validation passes.

**Bench:** the full protocol is `docs/xensiv-migration-bench-protocol.md`
(JV parity vs the 4.5.1 baseline, full calibration + cursor feel, Z-latch
across power cycles, the unseated-cable backoff, and the BLE battery
sign-off for a continuously-measuring sensor — the one honest trade).
