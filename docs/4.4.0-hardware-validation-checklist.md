# 4.4.0 hardware validation checklist — the bench session

The one hardware day the roadmap ledger says closes most of what's left.
Everything below is code-complete and simulator-tested; this session is
about feel, field behavior and the close-pending upstream issues. Work
top to bottom — each part assumes the one before it. Capture the app's
session log (Log ▸ Download) after every part; a failed expectation is
worth more with its log than without.

**Bench:** one LipSync V4 on firmware 4.3.0 (the update-path test needs
it as the *from* version), the app at the pushed `main` (or the deployed
site), a serial monitor (Arduino IDE / `screen`), optionally an Android
phone with a USB-C OTG adapter for part G.

---

## A. Update path: 4.3.0 → 4.4.0 (firmware-update features)

- [ ] **A1 — check + install.** Connect the 4.3.0 device, Firmware ▸ Check
  for updates. The local-build route: `localStorage['lipsync-fw-manifest-url']
  = '/firmware-manifest.json'` (dev server) after
  `dev/firmware/build-firmware.sh`. Install. Watch for: settings backup
  downloaded → UM-first entry (Hub screen shows the deliberate
  "Update mode" splash — not a frozen "Restarting") → bootloader port pick →
  flash → reconnect → **version verified as 4.4.0** → settings restored.
  **Pass:** the restore lands in one pass with **no "Timed out waiting for
  device response"** on SS/SL/AV (the post-flash first-writes failure the
  4.4.0 HID fix addresses). Any timeout here: save the log — it reopens
  update-item 2's residual with real data.
- [ ] **A2 — post-update app state.** Restrictions card active (not
  "needs firmware 4.4.0+"); timing windows loaded with values (1000/3000/
  8000); health check shows all five steps including I2C bus.
- [ ] **A3 — settings survived.** Compare the pre-update backup file with
  the post-update Export settings: every writable value identical.

## B. Input restrictions (roadmap item 11 — #21/#44/#68/#77)

For each toggle: set it **from the app**, verify on-device behavior, then
set it **from the Hub menu** (More ▸ Restrictions) and check the app's
checkbox follows (MANUAL sync).

- [ ] **B1 — SD, disable sip & puff.** A short puff does nothing at all:
  no click, no LED, no tone. Joystick still moves the cursor. Hub buttons
  still work. `DEBUG,5` (serial) still tracks sip/puff states — the
  diagnostics run, only the actions are gone. Re-enable → actions return.
- [ ] **B2 — MA, menu on hub buttons only.** A very long puff no longer
  opens the menu; buttons do. With the menu open (opened via buttons),
  sip/puff cannot navigate it. External switches also lose menu control.
- [ ] **B3 — LK, lock operating mode.** Hub menu ▸ Mode: selecting any
  mode refuses with the short error tone, no confirm page. **From the
  app**, mode switching still works (the caregiver path). Unlock after.
- [ ] **B4 — CF, freeze cursor during sip & puff.** Enabled: while
  holding a sip, deflect the stick — the cursor holds still; release and
  it moves. With SD also on, a sip must have *no* observable effect
  (no freeze either — CF only counts enabled inputs).
- [ ] **B5 — persistence + factory reset.** Power-cycle: restrictions
  retained. Factory reset (app ▸ Maintenance or FR,1:1): all four back to
  off, device boots unrestricted.
- [ ] **B6 — update round-trip.** With all four restrictions set,
  re-flash 4.4.0 (rebuild locally with a bumped version, or repeat A1
  with the same manifest): the restore re-applies all four.

## D. Input-state LED tier (roadmap item 16 — #43)

**Bench result (2026-10-19): D1 and D3 pass. D1 carries a hardware
finding that sharpens item 16's with-users question — see the note.**

- [x] **D1.** App ▸ Light feedback = Input state. Hold a puff: LEDs green
  in the first window, yellow after the long boundary, red in very-long;
  release → LEDs return to default, the action fires correctly. Repeat
  with the windows from C1 — the colors must follow the *user's*
  boundaries, not the compiled ones.
  *Pass (2026-10-19): the traffic light confirmed live — green → yellow →
  red across the held windows, clean return to default on release,
  following the user's windows. HARDWARE FINDING: the colors rendered
  only on the micro LED next to the USB-C port — the Hub's single RGB LED
  (LSOutput drives the three face LEDs by brightness alone; their color
  parameter is ignored because they are physically single-color, so they
  glowed steady red through every window and carried no window signal).
  The first bench user's read of the tier was exactly that confusion —
  "the LEDs are always red" — which redesigned the indicator: as of
  firmware 4.5.3 the face LEDs FILL left → middle → right as the hold
  crosses each window (1/2/3 — a count, the one message single-color LEDs
  can carry unambiguously) while the micro LED keeps the color, a
  dual-channel window indicator. RE-TEST on the 4.5.3 build: hold a puff
  through all three windows and watch the fill step 1 → 2 → 3 with the
  matching micro colors, then a clean return to default on release; the
  with-users pass confirms the feel.*
- [ ] **D2.** Restrictions interplay: with SD on, a sip shows nothing —
  no window LED for a gated input.
  *Not separately captured; its substance (an SD-gated input shows
  nothing at all) is B1's check — tick together with B1 when the
  restrictions session evidence is back-filled to the checklist.*
- [x] **D3.** Toggle back to Basic: classic action-keyed behavior.
  *Pass, de-facto: every bench session since 4.1.0 ran in the Basic tier
  and observed the classic action-keyed blinks (click blink, drag/scroll
  solid) on the face LEDs.*

## F. Flaky-sensor verification (item 12 — upstream #74)

- [x] **F1.** With the device running, partially unseat the joystick
  interface cable (the known wedge class — do it gently; 4.2.0+ is built
  to survive it). Expected: the device stays alive and responsive over
  serial, the display may glitch but the firmware keeps answering,
  "ERROR: Pressure sensors not responding" appears on serial, sip/puff
  stop firing actions, `BH,0:0` shows climbing recoveries / sensors
  marked 2, the app's health check flags it — and **no spontaneous mode
  changes or menu walks happen** during the flaky window (#74's ask).
- [x] **F2.** Re-seat the cable: sensors recover, inputs return, BH
  recovery count freezes (no reset).

**Bench result 2026-10-18 (firmware ac90b08): F passes.** Serial stayed
alive through the flaky window, "Pressure sensors not responding" printed
once, sip and puff self-disabled, BH marked the pressure sensor degraded (2),
the app's health check surfaced "1 warning", and NO spontaneous mode changes
or menu walks occurred — #74's ask. Re-seat + restart recovered with a green
health check. Known limitation documented (not blocking, see the session
log): booting with the cable deliberately unseated can wedge the serial path
a few seconds into an app connection; the device shows its safe-mode error
page, no longer reset-loops, and recovers fully once re-seated.
