# LipSync Connect

Browser-based configuration and monitoring tool for the **LipSync** assistive joystick mouse. Connect the LipSync over USB serial (Web Serial or a WebUSB fallback on Android), adjust sip/puff thresholds, deadzones, cursor speed, feedback, and Bluetooth settings, run device self-tests and a health diagnostic, calibrate the joystick — and check for and install firmware updates — all from a secure Chromium page with no install.

Part of the OpenAT Joystick Project by [Makers Making Change](https://www.makersmakingchange.com/), a program of [Neil Squire](https://www.neilsquire.ca/).

## Requirements

- A LipSync device running firmware v4.1 (the app's protocol is hand-tuned against it)
- A desktop browser with **Web Serial**: Chrome / Edge / Opera (macOS, Windows, Linux)
- On Android, Chrome with a USB-C / OTG cable uses the built-in **WebUSB** fallback
- **Not supported:** iOS, Firefox, Safari — the browser must be served over a secure context (HTTPS or `localhost`)

## Getting started (development)

```sh
cd dev
npm install              # dev tooling (also generated by the CI lockfile)
npm start                # HTTP on http://localhost:4443
npm run start:https      # HTTPS on https://localhost:4443 (auto-generates a self-signed cert via openssl)
npm run dev:local        # HTTP + live reload for app/ edits
```

`HOST`/`PORT` env vars override the bind address and port. Opening `https://localhost:4443` once and accepting the self-signed cert lets the browser treat the page as a secure context, which Web Serial requires.

Connect a LipSync, click **Connect**, choose the device (it appears as something like `XIAO nRF52840 Sense`), and wait for ~17 settings to load (~30 s). See the built-in Help card for troubleshooting.

## Deploy

The app is a static site that deploys as-is to Vercel. `app/vercel.json` sets the strict CSP/security headers and rewrites `robots.txt`. The service worker precaches every asset so the page works offline after the first visit.

## Firmware updates

The **Firmware** section compares the connected device's version against the latest published [LipSync release](https://github.com/makersmakingchange/LipSync/releases) (via a `firmware-manifest.json` asset built by the firmware repo's release pipeline) and can install the update in place:

- settings are backed up automatically (and downloadable) before anything is written
- the app restarts the device into its stock bootloader with a 1200-baud touch (no firmware-side changes needed; a double-tap-reset fallback is offered)
- the image is flashed over the bootloader's serial-DFU protocol — Web Serial on desktop, the same protocol over the WebUSB CDC shim on Android
- after reconnecting, the new version is verified and the backed-up settings are restored automatically

App-only DFU packages cannot touch the bootloader, so a failed update is always recoverable. In development, point the check at a local build with `localStorage['lipsync-fw-manifest-url'] = '/firmware-manifest.json'` (served by `dev/server.js` from `dev/firmware/dist/`) and build artifacts with `dev/firmware/build-firmware.sh`. To exercise the full auto-detection + download + flash flow against another repo's releases (e.g. a fork), set `localStorage['lipsync-fw-release-api']` to that repo's `https://api.github.com/repos/<user>/LipSync/releases/latest` instead — the manifest override takes precedence when both are set.

### Security notes

- Artifacts are fetched exclusively through `api.github.com` over TLS (GitHub release download URLs serve no CORS headers, so the release workflow also publishes them to a dedicated `firmware-binaries` branch the app reads via the contents/git-blob endpoints), and each package's sha256 is checked against the release manifest before flashing. Release-path installs require that checksum — our release pipeline always publishes one.
- The checksum guards the pipe (transport + GitHub), not the source: the manifest travels in the same repo it vouches for, so a compromised upstream repo or release workflow could publish arbitrary firmware. Meaningful hardening would be a signing key verified in-app; until then, the check protects against corrupted or tampered downloads only.
- "Flash local file…" trusts the file the user picks (that is its purpose). The package parser caps decompression at 8 MB — far above any real image — to defuse crafted zips.
- The settings backup downloaded before each update is the recovery path if anything interrupts the automatic post-update restore.

## Project layout

```
app/                      served application (front end)
  js/
    config/               shared constants (single source of truth)
    serial/               wire protocol, transport, command queue, read loop
      dfu/                serial-DFU protocol, transports, DFU package parsing
    services/             settings, calibration, self-test, health, hub mirror, log/export,
                          firmware update (check + flash wizard)
    plotting/             joystick plot, pressure gauge, live diagnostics
    ui/                   connection chrome, sections, theme, a11y, guard
    state/ modes.js       operating/communication mode state
  service-worker.js       offline precache
dev/                      dev server, lint/type/format configs, test runner entry
  firmware/               local firmware build script (arduino-cli → DFU zip/UF2/manifest)
tests/                    unit + integration tests (node) and firmware simulators
  harness/                DOM stubs, firmware + bootloader simulators, ESM load-order helpers
docs/                     scope and feature-list documents
```

A note on the module graph: `serial/` never imports `plotting/` or `ui/` layout code directly — endpoint renderers are registered into `services/registry.js` so the dependency graph stays acyclic.
